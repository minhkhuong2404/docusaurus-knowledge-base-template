# 🛡️ Network Tokenization & EMV 3-D Secure Architecture

Card-Not-Present (CNP) e-commerce transactions represent the primary frontier for card fraud. To protect cardholder data and prevent unauthorized transactions, the payment industry has converged on two complementary cryptographic pillars:

1. **EMVCo Network Tokenization**: Replaces static Primary Account Numbers with domain-restricted, cryptogram-backed surrogate tokens.
2. **EMV 3-D Secure 2.2 / 2.3**: Authenticates the cardholder directly with their issuing bank before the transaction is dispatched for authorization.

---

## 1. Vault Tokenization vs. EMVCo Network Tokenization

Historically, merchants and payment gateways stored raw card numbers in internal tokenization vaults, issuing proprietary surrogate tokens:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. Proprietary Merchant Vault Tokenization                                   │
│    - Gateway encrypts FPAN into an internal database vault.                 │
│    - Token is meaningful ONLY to that specific gateway.                     │
│    - ❌ When physical card expires, recurring payments fail.               │
│    - ❌ If vault is breached, cardholder data environment is exposed.       │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. EMVCo Network Tokenization (VTS / MDES)                                  │
│    - Global schemes (Visa, Mastercard) manage the authoritative vault.       │
│    - Issues a 16-digit DPAN (Device PAN) with channel domain restrictions.  │
│    - ✅ Automatic card lifecycle sync (re-issued cards update instantly).    │
│    - ✅ Every transaction requires a dynamic one-time cryptographic proof.  │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. EMVCo Network Tokenization Lifecycle

Network tokenization replaces the raw Funding PAN (**FPAN**) with a Device PAN (**DPAN**):

```
[Merchant / App / Apple Pay]                    [Scheme Token Service (VTS/MDES)]           [Issuing Bank]
             │                                                  │                                  │
             ├────── 1. Token Provisioning Request (FPAN) ─────►│                                  │
             │                                                  ├────── 2. Authorize Token ───────►│
             │                                                  │◄───── 3. Token Approved ─────────┤
             │◄───── 4. Issues DPAN + Initial Cryptogram ───────┤                                  │
             │                                                  │                                  │
   [Customer Taps / Pays Online]                                │                                  │
             │                                                  │                                  │
             ├────── 5. 0100 Auth (DPAN + Dynamic Cryptogram) ─►│                                  │
             │          (TAVV for Visa / DSRP for Mastercard)   │                                  │
             │                                                  │ [De-tokenizes DPAN to FPAN]      │
             │                                                  ├────── 6. 0100 Auth with FPAN ───►│
             │                                                  │◄───── 7. 0110 Auth Approved ─────┤
             │◄───── 8. 0110 Auth Response Forwarded ───────────┤                                  │
```

### Key Tokenization Components

* **FPAN (Funding Primary Account Number)**: The real 16-digit card number printed on the physical card. Never leaves the scheme's secure token vault.
* **DPAN (Device / Domain Primary Account Number)**: A 16-digit surrogate number generated by the Token Service Provider (TSP) that passes the Luhn check and routes like a normal card.
* **Token Requester ID (TRID)**: An 11-digit identifier issued by EMVCo identifying the entity requesting the token (e.g., Apple, Google, Netflix, Stripe).
* **Dynamic Cryptograms (TAVV / DSRP)**:
  * **TAVV (Token Authentication Verification Value)**: Visa's dynamic cryptogram generated per transaction.
  * **DSRP (Digital Secure Remote Payment)**: Mastercard's dynamic cryptogram.
  * *Security Guarantee*: Even if an attacker intercepts a DPAN and cryptogram, the cryptogram is single-use and cannot be replayed.
* **Domain Restrictions**: A network token is cryptographically bound to a specific usage channel:
  * *E-Commerce Only*: Cannot be used at physical POS terminals.
  * *Merchant-Specific*: Bound to a specific merchant TRID; useless if stolen from a merchant database.
  * *Device-Bound*: Bound to the Secure Element (eSE) of a single iPhone or Android device.

### Automatic Account Updater (Lifecycle Sync)
When a customer loses their physical card or it expires, the issuing bank issues a new physical card with a new FPAN.
- Under legacy systems, all stored subscriptions (Netflix, Spotify, AWS) fail until the user manually types new details.
- Under EMVCo Network Tokenization, the scheme vault updates the mapping to the new FPAN instantly. **The DPAN remains unchanged**, resulting in zero payment disruption.

## 3. Digital Wallets: Apple Pay & Google Wallet Architecture

Modern mobile wallets leverage network tokenization combined with on-device hardware security:

```
┌────────────────────────────────────────────────────────┐
│                   SMARTPHONE DEVICE                    │
│                                                        │
│  [Mobile App / Apple Wallet UI]                        │
│          │                                             │
│  [Biometric Sensor: Face ID / Touch ID (CDCVM)]        │
│          │                                             │
│  [Hardware Secure Element (eSE / Titan M)]             │
│    ├── Stores DPAN                                     │
│    ├── Stores Applet Private Keys                      │
│    └── Computes dynamic cryptogram during NFC tap      │
└────────────────────────────────────────────────────────┘
```

1. **Secure Element (eSE)**: Tamper-resistant hardware chip isolated from the main smartphone operating system (iOS/Android). Private keys cannot be extracted even with root/jailbreak access.
2. **Host Card Emulation (HCE)**: Used by some Android implementations where credentials reside in an encrypted cloud service and short-lived limited-use keys (LUK) are synced to the phone.
3. **Consumer Device Cardholder Verification Method (CDCVM)**: Replaces terminal PIN entry. Biometric authentication directly on the phone satisfies the Cardholder Verification requirement for unlimited transaction amounts.

## 4. EMV 3-D Secure 2.2 / 2.3 Protocol

EMV 3-D Secure (**3DS**) introduces an authenticated three-domain messaging architecture between the **Acquirer Domain**, **Interoperability Domain**, and **Issuer Domain**:

```
[Acquirer Domain: Browser / App / 3DSS]      [Interoperability: Directory Server]     [Issuer Domain: ACS]
                   │                                          │                                │
                   ├────── 1. AReq (Auth Request with 150+ data signals) ─────────────────────►│
                   │                                          │                                │
                   │       [ACS Risk Engine: Geolocation, Device Fingerprint, History]         │
                   │                                          │                                │
                   │◄───── 2. ARes (Frictionless: Approved with CAVV/AAV Cryptogram) ──────────┤
                   │                                - OR -                                     │
                   │◄───── 3. CReq / CRes (Challenge Flow: In-App Push / SMS OTP) ─────────────┤
```

### Protocol Participants

1. **3DS Server (3DSS)**: Managed by the merchant or payment gateway. Collects browser telemetry and dispatches authentication requests.
2. **Directory Server (DS)**: Operated by the card scheme (Visa Secure, Mastercard Identity Check). Routes authentication requests to the appropriate bank.
3. **Access Control Server (ACS)**: Hosted by the issuing bank. Contains the risk scoring engine and presents authentication challenge screens to cardholders.

## 5. Frictionless vs. Challenge Flows & Liability Shift

### Frictionless Flow (90%+ of Transactions)
* The 3DSS supplies over 150 transaction data attributes to the issuer:
  * Device IP, Browser User-Agent, Screen Resolution, Timezone.
  * Device Fingerprint & Hardware Serial Number.
  * Cardholder Shipping vs. Billing Address match.
  * Transaction history and velocity profile.
* If the issuer's risk score is low, the ACS returns an immediate `ARes` with status **`Y` (Authentication Successful)** and an authentication cryptogram (**CAVV** / **AAV**).
* Total elapsed duration: **100ms - 250ms**. The customer experiences zero friction or redirects.

### Challenge Flow (High Risk or Regulatory Mandate)
* If the transaction appears anomalous (e.g. login from a new country, high amount), the ACS requests a challenge.
* The user authenticates via **Out-of-Band (OOB)** mobile banking push notification (biometric Face ID) or SMS One-Time Password (OTP).

### The Global Liability Shift Rule
When an e-commerce merchant successfully passes a transaction through 3-D Secure:
- **Fraud Liability Shifts to the Issuing Bank**: If the cardholder subsequently claims the transaction was unauthorized (Reason Code `10.4`), the issuing bank absorbs the fraud loss. The merchant is protected against chargebacks.

## 6. PSD2 Strong Customer Authentication (SCA) & Exemptions

In the European Economic Area (EEA) and United Kingdom under PSD2/PSR, electronic transactions legally require two of three authentication factors:
1. **Knowledge**: Something you know (password, PIN).
2. **Possession**: Something you have (phone, hardware token, secure element).
3. **Inherence**: Something you are (fingerprint, facial recognition).

### Legal SCA Exemptions Engine:
Merchants can request exemptions in the `AReq` message to skip challenges:
- **Low-Value Exemption**: Transactions under €30 (up to a cumulative €100 or 5 consecutive transactions).
- **Transaction Risk Analysis (TRA)**: If the acquirer's overall fraud rate is below regulatory thresholds (e.g. under 0.01% for transactions up to €500).
- **Trusted Beneficiaries**: Cardholders whitelist specific merchants inside their banking app.
- **Recurring Subscriptions**: Fixed-amount recurring subscriptions after the first transaction.

## 7. PCI-DSS Scope Reduction Architecture

The Payment Card Industry Data Security Standard (**PCI-DSS v4.0**) imposes strict controls on systems that store, process, or transmit cardholder data.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ PCI-DSS COMPLIANCE MATRIX                                                   │
│                                                                             │
│ SAQ A (Lowest Burden - ~30 Controls):                                       │
│   - Merchant uses iframe or Hosted Fields provided by certified gateway.     │
│   - Card data never touches merchant web server memory or logs.             │
│                                                                             │
│ SAQ A-EP (Moderate Burden - ~160 Controls):                                 │
│   - Merchant controls JavaScript form that posts directly to gateway.       │
│   - Vulnerable to client-side script injection (Magecart attacks).          │
│                                                                             │
│ SAQ D (Maximum Burden - 300+ Controls):                                     │
│   - Merchant receives, decrypts, or stores raw PANs on internal servers.     │
│   - Requires full network segregation, file integrity monitoring, and HSMs. │
└─────────────────────────────────────────────────────────────────────────────┘
```

By leveraging **Hosted Fields + EMVCo Network Tokenization**, modern fintech architectures achieve full **SAQ A** eligibility, eliminating card data compromise risk from application infrastructure.
