# Engineering Knowledge Base

This website is a practical, continuously growing knowledge base for software engineers.
It is designed to help you learn faster, make better technical decisions, and revisit core concepts when you need them as a reference.

The content focuses on clear mental models, engineering trade-offs, and implementation-oriented explanations rather than theory alone.

Please note that most of the content is still being developed, but the structure and learning paths are in place to guide you through the material as it grows.

## Note on Content Generation
Most of the content is generated by AI, but it is based on real-world engineering experience and is intended to be a practical resource for engineers at all levels.

This also helps speed up interview preparation, since you can quickly review core concepts and trade-offs before interviews.

## Interview Focus

When using this site for interview preparation, prioritize:

- Core principles before framework details (for example, consistency, scalability, isolation, and fault tolerance)
- Trade-off reasoning (why one design is chosen over alternatives)
- Failure-mode thinking (timeouts, retries, idempotency, partial failures, and observability)
- Practical system decisions (data modeling, API boundaries, deployment and rollback strategy)

Good interview answers usually connect three layers:

1. Concept: what it is and why it exists
2. Design choice: when to use it and what trade-off it introduces
3. Operations: how it behaves in production under load or failure

## Interview Traps

Common mistakes to avoid:

- Giving definition-only answers without design trade-offs
- Ignoring scale assumptions (QPS, payload size, data growth, latency target)
- Overusing buzzwords without clear architecture boundaries
- Treating consistency, reliability, and cost as independent concerns
- Forgetting operational details (monitoring, alerting, runbooks, rollback)

Quick self-check before interviews:

1. Can you explain your design choices with at least one alternative?
2. Can you describe what breaks first at 10x traffic?
3. Can you explain how you would detect and recover from failures?
4. Can you justify your decision in terms of both user impact and engineering cost?
